# 任务：用 tdict 读懂一批 T100 ERP 源码，并如实评价这个工具

你是一名刚拿到某个内部命令行工具的开发者。请用这个工具去读懂一批 T100(Genero/4GL) ERP 源码，然后**如实**评价这个工具和它的使用说明。评价会被用来改进工具，所以「说好话」没有任何价值——**卡壳、报错、看不懂、被说明误导，这些才是最值钱的产出**。

## 先确认你有执行能力

你需要能执行命令、读写文件。**如果你没有终端/文件访问能力，直接回一句「无法执行」就结束，不要凭想象编造任何结果。**

## 你手上的材料（只有这些）

| 用途 | 路径 |
|---|---|
| 工具 | `D:\APPS\tdict-portable\tdict.exe`（该目录已在 PATH 里，直接写 `tdict` 也可以） |
| 用户文档 | `D:\APPS\tdict-portable\README.md` |
| 使用说明（本次要评价的「提示词」） | `D:\APPS\tdict-portable\skills\tdict\SKILL.md`、`D:\APPS\tdict-portable\skills\erp-code-reader\SKILL.md` |
| 待读源码 | `D:\t100_source_code`（约 2 万个 `.4gl`） |
| 工具自带的本地数据 | `D:\APPS\tdict-portable\erp_data.db` |

## 硬性约束

1. **只看上面的材料**。不要读 `D:\APPS\tdict-portable` 与 `D:\我的项目\TDictCli` 里的程序实现代码、不要读它们的 git 历史——你的评价必须基于「用户能看到的东西」（文档 + 工具的实际行为）。偷看实现会让评价失真。
2. 源码树 `D:\t100_source_code` **只读**，不要修改任何源文件；工具目录除报告外也不要写。
3. **不要提问**，自己解决；解决不了就如实记成「卡住了」。
4. 命令都在 shell 里执行（Windows + Git Bash，路径含中文注意引号）。大文件不要整篇读进上下文，按需分段/搜索；整体规模控制在几十次工具调用量级，别在单个样本上钻牛角尖。
5. 所有结论要能追溯到具体命令或源码行，**标清来源**：`[工具]`=工具输出、`[源码]`=你读的 `.4gl`、`[推测]`=你猜的。
6. **全程记录你执行的每条命令**（包括失败的），最后附在报告里。

## 任务

### 任务 1：按说明上手

只读上面那三份文档，让工具跑起来、确认能查到数据。如实记录你做了什么、哪些命令报错、最后怎么跑通的。**这段过程本身就是最重要的评价材料之一**（说明写没写清楚）。

### 任务 2：用工具回答这几个「用户目标」

不要只翻命令清单，**按文档自己找路**；每个问题都要记录你为了找到那条命令花了多少步。

1. `aapi011` 这个程序是做什么的？有哪些作业在使用它？
2. 想知道「对账」相关的**数据表**有哪些，怎么找？
3. `D:\t100_source_code\erp\aap\4gl\aapq110_01.4gl` 做什么？访问哪些表？用到哪些校验/开窗/消息？
4. `D:\t100_source_code\com\qry\4gl\q_adzi052.4gl`（1,274 行）做什么？
5. `D:\t100_source_code\com\lib\4gl\cl_abi.4gl`（2,073 行）做什么？
6. `D:\t100_source_code\erp\aap\4gl\aapi011.4gl`（6,592 行）访问哪些表？主要做什么？
7. 本机的工具数据齐不齐？缺什么、怎么补？

每个问题写：**结论 + 你用了哪条命令 + 哪些是工具给的、哪些是你读源码补的**。

### 任务 3：对照实验（工具 vs 裸读）

从任务 2 里挑**一个**文件，就「它访问哪些表 + 这些表分别做什么」这一个问题，**完全不用工具**、纯读源码回答一遍。然后比较两条路径：步数/耗时、准确度差异、哪个更省 AI 的上下文。

### 任务 4：自选探索

在 `D:\t100_source_code\erp\` 里**挑一个不是 aap 的模块**，随便挑一个你没读过的程序，用工具在尽量少的步数内说清它的用途和主要数据依赖。记录：花了多少步、哪些命令真正有用、哪些白费。

### 任务 5：评价（核心产出）

1. **摩擦点清单** —— 逐条，每条固定四段：
   - 我期望什么 →
   - 实际发生什么（**原始命令 + 原始输出片段**）→
   - 我怎么绕过去的 / 绕不过去 →
   - 严重度（挡路 / 烦人 / 小瑕疵）
2. **打分（1–5 分，每项给理由）**：上手难度、输出可读性、信息完整度、相对裸读源码的增益、SKILL.md 可用性、README 可用性
3. **工具改进建议**：具体到「加什么命令 / 改什么输出 / 补什么数据」，按对「读懂代码」的价值排序，最多 8 条
4. **使用说明(SKILL.md)改进建议**：哪一句会误导、缺什么、该怎么写（**给出你建议的原文**），最多 8 条
5. **一句话结论**：同事要读 ERP 源码，你推不推荐用它？为什么？

## 输出

1. 把**完整报告**写成 Markdown，存到 `D:\tdict-eval\report-<你的模型名>.md`（目录不存在就创建；文件名带模型名，例如 `report-glm-4.6.md`）。报告要含原始命令、原始输出片段与最后的命令流水。
2. 在你的回复里**只给**：报告文件路径 + 打分表 + 5 条最值得处理的发现（每条一句话）。**不要把整篇报告贴进回复。**
